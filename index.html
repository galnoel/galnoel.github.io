How the game server decides a match

Follow the responsibilities inside YUDHA’s real-time game backend.

PlayerFlutter client
AuthorityNestJS game backend
Shared stateRedis

The client connects to the game backend.

Socket.IO carries real-time battle interactions between the Flutter app and the NestJS game service. A separate app backend handles practice and progress through REST APIs.

The server validates game actions.

The game backend checks an action before accepting it. I kept validation on the server so the client does not decide which game actions count.

Redis holds matchmaking and game state.

I used Redis for matchmaking and game state, with Supabase PostgreSQL for persistent data. Each has a distinct responsibility in the system.

The game server determines the outcome.

The backend owns the battle result. Keeping this decision alongside action validation makes the server the authority for a competitive match.

Problem
Keep matchmaking, battle state, and study progress consistent across concurrent requests and player disconnects.
My role
Tech Lead & Backend Engineer. I owned the system architecture, both NestJS services, the Supabase database, authentication, and deployment on Railway.
Approach
The app backend serves REST APIs for practice and progress tracking. The game backend uses Socket.IO for real-time battles, Redis for matchmaking and game state, and Supabase PostgreSQL for persistent data.
Key decision
The server validates game actions before accepting them and determines the battle outcome.
Result

Making document-grounded legal research easier to retrace

I built Lexara, a deployed research assistant that combines a fine-tuned Qwen 2.5 7B model with retrieval over more than 1,900 pages of Indonesian labor-law documents.

Problem
Retrieve relevant passages from a large legal-document collection, then make each answer easy to verify against its source.
My role
Built the model-training pipeline, hybrid retrieval system, and the responsive Lexara research interface.
Approach
Fine-tuned Qwen 2.5 7B with QLoRA and Group Relative Policy Optimization (GRPO), using custom rewards for structured reasoning.
Key decision
Combined keyword search (BM25) and vector search (ChromaDB) with Reciprocal Rank Fusion. HyDE query expansion and parent-child chunks add retrieval context.
Retrieval checks
Added FlashRank reranking, confidence thresholds, and a DuckDuckGo search fallback.
Result
Published the merged 16-bit model on Hugging Face Hub and deployed Lexara on Vercel with research prompts, document filtering, backend status, and traceable references.

Fish freshness: Multimodal classifier JUL–AUG 2025 Image and gas-sensor fusion for tuna freshness classification, with 84.3% validation macro F1. Multimodal transformersPyTorch · DINOv2 · Fusion Transformers Read case study ↗

Combining images and sensor readings to classify freshness

For the GEMASTIK XVIII qualifying round, our team built a tuna freshness classifier that combines images with electronic-nose sensor readings. I handled image preprocessing.

Problem
Combine visual and gas-sensor signals while preserving useful information from each modality.
My role
I prepared the image inputs for the model by extracting capture timestamps, checking image integrity, augmenting the dataset, and standardizing image sizes.
Approach
Aligned DaFiF images and sensor streams by timestamp, filtered anomalies, and combined a DINOv2 vision transformer with an MLP sensor encoder.
Key decision
Aligned the modalities with a CLIP-style contrastive loss, then used bidirectional cross-attention to fuse them. Focal Tversky Loss addressed class imbalance.
Result
On the tuna validation split, the team’s model achieved 85.4% accuracy, 84.3% macro F1, and 92.7% F1 for the “Marginal” freshness class.
Model interpretation
Used Grad-CAM visualizations to inspect the image regions influencing predictions.

Grad-CAM evidence over vision tokens used to inspect the model’s spatial focus.

Javanese script: Handwriting classifier OCT 2025 A 20-class handwriting model built during a five-hour competition challenge. Computer visionPyTorch · CoaT · Captum Read case study ↗

Recognizing handwritten Javanese script under time constraints

During the five-hour GEMASTIK XVIII final challenge, I worked as the modeler on a pipeline for 20 handwritten Javanese script classes using Co-Scale Conv-Attentional Transformers (CoaT).

Problem
Classify 20 handwritten script categories in a time-limited challenge with imbalanced training data.
My role
I benchmarked model architectures, implemented two-stage fine-tuning with Focal Loss, and inspected predictions with Captum Integrated Gradients.
Approach
Compared CoaT, Swin, and EfficientNet. Trained with frozen patch embeddings followed by progressive fine-tuning using AdamW and Kornia Focal Loss.
Key decision
Used macro F1 to evaluate performance across classes, and Captum Integrated Gradients to inspect stroke-level attribution and possible shortcut learning.
Result
The final CoaT model achieved 96.7% validation macro F1 across 20 classes.
