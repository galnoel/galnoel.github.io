### 1. YUDHA — Exam preparation platform

**Period:** MAR–SEP 2026

**Portfolio category:** Featured project

**Focus:** Backend engineering

**Card summary:** I led the architecture and built both NestJS backends for real-time exam practice.

**Headline outcome:** Team placed 2nd · PIDI DIGDAYA Hackathon 2026

#### Keeping competitive exam practice in sync

YUDHA (Your Ultimate Digital Hiring Arena) is a Flutter learning arena for Indonesian civil-service (CPNS) and state-owned-enterprise (BUMN) applicants, combining aptitude-test practice, real-time quiz duels, progress tracking, and AI interview preparation. As tech lead and backend engineer, I led the architecture and built the app and real-time game backends.

**Problem:** Keep matchmaking, battle state, and study progress consistent across concurrent requests and player disconnects.

**My role:** Tech Lead & Backend Engineer. I owned the system architecture, both NestJS services, the Supabase database, authentication, and deployment on Railway.

**Approach:** The app backend serves REST APIs for practice and progress tracking. The game backend uses Socket.IO for real-time battles, Redis for matchmaking and game state, and Supabase PostgreSQL for persistent data.

**Key decision:** The server validates game actions before accepting them and determines the battle outcome.

**Result:** I delivered the app and game backends and published the Android release on Google Play. The team placed 2nd at PIDI DIGDAYA x HACKATHON 2026.

**Project scope:** The Open Beta product includes a Learning Center, Standard, Focus, and Speed practice modes, progress tracking, and company- and role-specific AI interviews with text or voice answers. AI and voice availability depends on backend provider configuration.

#### Game-server architecture walkthrough

Flow: Flutter client (player) → NestJS game backend (authority) → Redis (shared state).

1. **The client connects to the game backend.** Socket.IO carries real-time battle interactions between the Flutter app and the NestJS game service. A separate app backend handles practice and progress through REST APIs.

2. **The server validates game actions.** The game backend checks an action before accepting it. I kept validation on the server so the client does not decide which game actions count.

3. **Redis holds matchmaking and game state.** I used Redis for matchmaking and game state, with Supabase PostgreSQL for persistent data. Each has a distinct responsibility in the system.

4. **The game server determines the outcome.** The backend owns the battle result. Keeping this decision alongside action validation makes the server the authority for a competitive match.

**Technology stack and methods:** NestJS; Socket.IO; Upstash Redis; Supabase PostgreSQL; Railway

### 6. Fish freshness: Multimodal classifier

**Period:** JUL–AUG 2025

**Portfolio category:** Additional case study

**Focus:** Multimodal transformers

**Card summary:** Image and gas-sensor fusion for tuna freshness classification, with 84.3% validation macro F1.

#### Combining images and sensor readings to classify freshness

For the GEMASTIK XVIII qualifying round, our team built a tuna freshness classifier that combines images with electronic-nose sensor readings. I handled image preprocessing.

**Problem:** Combine visual and gas-sensor signals while preserving useful information from each modality.

**My role:** I prepared the image inputs for the model by extracting capture timestamps, checking image integrity, augmenting the dataset, and standardizing image sizes.

**Approach:** Aligned DaFiF images and sensor streams by timestamp, filtered anomalies, and combined a DINOv2 vision transformer with an MLP sensor encoder.

**Key decision:** Aligned the modalities with a CLIP-style contrastive loss, then used bidirectional cross-attention to fuse them. Focal Tversky Loss addressed class imbalance.

**Result:** On the tuna validation split, the team’s model achieved 85.4% accuracy, 84.3% macro F1, and 92.7% F1 for the “Marginal” freshness class.

**Model interpretation:** Used Grad-CAM visualizations to inspect the image regions influencing predictions.

**Technology stack and methods:** PyTorch; DINOv2 / ViT; MLP; Fusion Transformers; Contrastive Learning; Focal Tversky Loss; Grad-CAM

**Problem:** Classify 20 handwritten script categories in a time-limited challenge with imbalanced training data.
